# Spalk fork of Zitadel

This fork adds a v2 `MoveUser` API (`zitadel.user.v2.UserService/MoveUser`) that moves a human user to another organisation, keeping their ID, credentials, MFA, passkeys and IdP links. Spalk needs it because upstream Zitadel can't change a user's organisation.

It also patches the login UI (`apps/login`): see [The login UI patch](#the-login-ui-patch).

From `v4.19.4-spalk.7`, the login UI also has a **"Keep me signed in"** checkbox (unticked by default) on the password page, the password registration and every IdP sign-in (the passkey page's prompt opens on load, so only its IdPs ask). On the loginname page it sits under the loginname and also serves the IdPs; the choice goes with the loginname in the same `remember_me_intent` cookie, so the password page opens ticked and an IdP the loginname sends the user to gets it. A ticked session gets the login policy's check lifetime and its entry goes in a second, persistent `sessions_remembered` cookie that expires with it; an unticked one stays in the browser-session `sessions` cookie and lives at most `ZITADEL_LOGIN_UNREMEMBERED_SESSION_LIFETIME` (default `24h`). Reads take the union of both cookies, and writes split the entries between them. The IdP choice crosses the round trip in a one-hour `remember_me_intent` cookie. The choice is also written to the session's metadata as `spalk:remember` = `true`, which Spalk's API reads with `GetSession` on the ID token's `sid`. These changes are marked `// Spalk:` in `src/lib/cookies.ts`, `src/lib/server/cookie.ts`, `src/lib/zitadel.ts`, `src/lib/server/{password,register,idp,loginname}.ts`, `src/components/remember-me.tsx` and the forms and pages that use it.

- **Branch:** `spalk` (this fork's default branch), rebased on an upstream release tag (currently `v4.19.4`).
- **Tags and images:** `v<upstream version>-spalk.<n>`, e.g. `v4.19.4-spalk.1`. The manually run **Spalk publish image** workflow (`.github/workflows/spalk-publish.yml`) calls `.github/workflows/spalk-publish-image.yml` at a pinned commit, which builds the API image and the login UI image (from `apps/login`, as upstream's `pack.yml` does) on GitHub's arm64 runner and pushes both, tagged with the fork's tag, to Spalk's private ECR. Spalk's AWS role trusts only that file at the commits spalk-stack lists in `publish_workflow_shas`.
- **Go SDK:** [SpalkLtd/zitadel-go](https://github.com/SpalkLtd/zitadel-go) adds the `MoveUser` client.
- **Upstream workflows:** disable them in this fork's Actions settings; they need Zitadel's own runners and secrets.
- **How Spalk deploys it:** `docs/infra/zitadel-fork.md` in Spalk's monorepo.

## The login UI patch

Upstream's login v2 picks a user's method after the username: a passkey, then a linked identity provider, then a password. So a user with both a password and a Google link was sent straight to Google, with no way to type their password. The fork changes that, in commit `9781dde4176` on `spalk`:
- **`apps/login/src/lib/server/loginname.ts`** (`sendLoginname`, the multi-method branch): a user with a password, when the login settings allow local authentication, goes to `/password` with the same parameters as a password-only user. A passkey still wins. A user without a password, or whose organisation doesn't allow local authentication, is still redirected to their IdP, as is an IdP-only user (the single-method switch, unchanged).
- **`apps/login/src/app/(login)/password/page.tsx`** and **`apps/login/src/app/(login)/passkey/page.tsx`** render `SignInWithIdp` below the form, as the loginname page does: the organisation's active IdPs, when `allowExternalIdp` is set, under the existing "or sign in with" label. No translations were added. The passkey page has it so that a user with a passkey and Google can still reach Google from a device without their passkey; its "Use password" button is unchanged.
- **Signing in through the button** starts a normal IdP login (`redirectToIdp`, no `sessionId`, so not a link flow). Zitadel matches the returned identity to the existing user by their IdP link and the login creates a session for them (`handleUserExists` in `apps/login/src/lib/server/idp-intent.ts`).
- **A username on the registration form,** from `v4.19.4-spalk.3`, commit `622b5b0bb` (`apps/login/src/components/register-form.tsx`): a required field that can't contain `@`, carried through `/register/password` to `registerUser` and `addHumanUser`, which sends it as the username instead of the email. When Spalk's user-creation hook refuses it as taken, `registerUser` shows the hook's message rather than "Could not create user" (any `AlreadyExists`, without Zitadel's error ID). The form's tests are in `src/components/register-form.test.tsx`.
- **The account picker finds moved users,** from `v4.19.4-spalk.4`, commit `cf20ffdfd` (`apps/login/src/components/session-item.tsx`): picking an expired session looks its login name up in every organisation, not the one the session recorded. That is where the user was when the session was created, and Spalk moves users (a self-registered user into their personal organisation at first login), so a moved user was unknown there and sent to that organisation's only IdP, Google. Usernames are unique instance-wide (`user_login_must_be_domain` is off), so the name alone finds them.
- **A wrong password says so,** from `v4.19.4-spalk.5`, commit `34dff7a55` (`apps/login/src/lib/server/password.ts`, `cookie.ts`): upstream's password page swallowed a failed session update and checked the password again on a new session, whose error had no failed-attempt count, so a wrong password showed "Could not create session for user" and counted twice. The session update's wrong password is now answered as one, and `createSessionAndUpdateCookie` keeps the count too (`passwordAttemptsHandler`). Tests: `password-send.test.ts`, `cookie.test.ts`.
- **An invite's registration takes the invited email,** from `v4.19.4-spalk.5`, the same commit (`apps/login/src/lib/server/flow-initiation.ts`): the `prompt=create` redirect to `/register` carries the auth request's `login_hint`, which the Live Sync API sets to the invited address, as `email`. Test: `flow-initiation.test.ts`.
- **The password pages find moved users,** from `v4.19.4-spalk.6`, commit `227deef87` (`apps/login/src/lib/server/password.ts`): `sendPassword` and `resetPassword` look the user, and the session cookie, up by login name alone. The organisation the login-name step passes on can be the one Spalk has just moved the user out of (at first login), and scoped to it they were unknown: a correct password was refused with "Could not verify password". Test: `password-send.test.ts`.
- **An IdP sign-up missing a name is created in one call,** from `v4.19.4-spalk.6`, which was moved to it on 28/10/26 (`apps/login/src/lib/server/register.ts`, `src/lib/idp-create-user.ts`, `src/components/register-form-idp-incomplete.tsx`): Google leaves out the family name of an account that has none, and login v2 then asks for the names on its complete-registration form. Upstream created that user from the form, with an editable, unverified email, and linked Google in a second call, which Spalk's user-creation hook refuses for an unverified email: the person was left with an account that had neither a password nor Google, and held their email. `registerUserAndLinkToIDP` now retrieves the IdP intent again and creates the user from it, as auto-creation does (`buildCreateUserRequest`, moved out of `idp-intent.ts` to share it): Google's email, verified as Google says, and the Google link in the same `CreateUser`, with only the names from the form. The form shows the email read-only. Tests: `register.test.ts`, `register-form-idp-incomplete.test.tsx`.
- **An organisation's own login page,** from `v4.19.4-spalk.7` (`apps/login/src/lib/server/flow-initiation.ts`): the Live Sync API sends `urn:zitadel:iam:org:id:<id>` (and `urn:zitadel:iam:org:idp:id:<idp>` for a customer's SSO link) from Content Hub's `/login?org=<id>&idp=<idp>`. Upstream took only numeric organisation IDs from the scope, and Spalk's are UUIDs, so the organisation was dropped and its branding and IdPs never shown. Test: `flow-initiation.test.ts`. "Register new user" on an organisation's page is upstream's: spalk-stack's login policies hide it (registration is off in the instance default, which Spalk's organisations follow, and on in "Self-registered"'s own policy).
- **An organisation's own SSO can sign people up,** from `v4.19.4-spalk.7` (`apps/login/src/lib/server/register.ts`): when the IdP leaves out a name, login v2 sends the person to its complete-registration form, whose `registerUserAndLinkToIDP` refused them unless the organisation's login settings allow registration, and Spalk's organisations don't. It now also takes the IdP's own "creation allowed", as login v2's other IdP paths do, read from the intent's IdP rather than the form. Spalk's user-creation hook still refuses a sign-up into an organisation through any IdP but its own. Test: `register.test.ts`.
- **An unknown login name on an organisation's page goes only to that organisation's own IdP,** from `v4.19.4-spalk.8` (`apps/login/src/lib/server/loginname.ts`, `redirectUserToIDP`): upstream sends a login name it can't find on an organisation's page (`?organization=`, or one found by domain discovery) on to the organisation's only active IdP that can create users, so a first-time SSO user is created there. On a Spalk organisation's page that IdP is the instance's Google, which can't sign anyone up into it, so a mistyped or outside username landed on Google's sign-in. Only an IdP the organisation owns (`GetIDPByID`'s resource owner) is used now; otherwise the page says the user isn't found. An IdP that can't be read isn't used. Test: `loginname.test.ts` (`User not found scenarios`).
- **A login refused for being outside the requested organisation tells the app,** from `v4.19.4-spalk.9` (`apps/login/src/lib/oidc.ts`, `loginWithOIDCAndSession`): Zitadel refuses to link a session to an auth request whose organisation scope the user isn't in (`COMMAND-59ljd`, `Errors.User.NotAllowedOrg`). Login v2 treated that, like every `FailedPrecondition`, as an auth request already handled and sent the user to the login policy's default redirect, Content Hub's `/login`, which started the login again: an endless loop. It now fails the auth request with `access_denied` ("This account isn't a member of the organisation it tried to log in to") and redirects to the app's `redirect_uri` with it. Other `FailedPrecondition`s are unchanged, and SAML has no organisation scope. Test: `oidc.test.ts`.
- **An IdP sign-up the user-creation hook refuses shows the hook's message**, from `v4.19.4-spalk.9` (`apps/login/src/lib/server/idp-intent.ts`, `handleAutoCreation`): when Spalk's user-creation hook refused an auto-created IdP user, upstream sent the person to `/idp/<provider>/failure` with a generic "Login failed". A `CreateUser` error that is an Actions v2 target's refusal (Zitadel's `EXEC-reUaUZCzCp` or `EXEC-bmhNhpcqpF`) is now returned to the IdP process page as its message, without Zitadel's error ID, which the page shows; other failures are unchanged. Test: `idp-intent.test.ts`.
- **An IdP sign-up gets one email code, not two**, from `v4.19.4-spalk.9` (`apps/login/src/lib/idp-create-user.ts`, `withoutCreateEmailCode`; `src/lib/server/idp-intent.ts`): when the IdP hasn't verified the email, the intent's `CreateUser` request asks Zitadel to send a code, and auto-creation then signs the user in through `createNewSessionFromIdpIntent`, whose `checkEmailVerification` sends a second code that replaces the first, so the first emailed code was rejected. Auto-creation now creates that email as unverified (`isVerified: false`, as ordinary registration does), leaving the sign-in's code as the only one. A verified email is unchanged. The complete-registration form's `registerUserAndLinkToIDP` keeps the intent's `sendCode`: it doesn't send a code itself, so Zitadel's is already the only one. Test: `idp-intent.test.ts` (`CASE 4: Auto-creation of user`).
- **SCIM user creation runs `CreateUser`'s Actions v2 executions,** from `v4.19.4-spalk.10` (`internal/api/scim/resources/user_execution.go`, `user.go` `Create`; `cmd/start/start.go` and `internal/api/scim/server.go` pass it the target key, signing key and HTTP client): SCIM created users with the command directly, so the request and response targets of `/zitadel.user.v2.UserService/CreateUser`, which every other way of creating a user runs, never ran, and Spalk's user-creation hook didn't see SCIM's users. SCIM's create (not replace or patch; a Bulk create too) now builds the equivalent `CreateUserRequest` (the SCIM path's `organizationId`, `username`, `human.profile`, `human.email` with `isVerified` when SCIM's `EmailVerified` is on, `human.phone`, `human.password` unless ignored on create, and SCIM's `urn:zitadel:scim:*` entries in the top-level `metadata`; no `userId`) and posts it to the request targets with the SCIM caller as `userID` and the path's organization as `orgID`, as a gRPC call's payload has them (no `headers`). The user created is the one the returned request describes, converted as `CreateUser` converts it (`CreateHumanRequestToAddHuman`, moved out of `internal/api/grpc/user/v2/human.go`'s `createUserTypeHuman`): its `userId`, `username`, profile, email, phone, password and metadata, SCIM's `active` kept. A returned request for another organization or a machine is refused (400). A refusal (`forwardedStatusCode`/`forwardedErrorMessage`) is SCIM's error with that message: 409 `uniqueness`, 403, 400 `invalidValue`, and 400 for a 5xx (Zitadel's PreconditionFailed). After the creation the response targets get that request and a `CreateUserResponse` (`id`, `creationDate`); SCIM answers with its own resource, so their reply is not used. With no executions for `CreateUser` nothing changes. The targets are called by `connect_middleware.ExecuteRequestTargets`/`ExecuteResponseTargets`, moved out of the connect execution interceptor. Tests: `internal/api/scim/resources/user_execution_test.go`.
- **The generic OIDC IdP can trust its emails ("Email verified")**, from `v4.19.4-spalk.10` (API and console, not the login UI): the Azure AD type's `email_verified` option, for the generic OIDC type, so a customer's IdP that doesn't send `email_verified` (or sends `false`) still gives verified emails: auto-linking by email works and the first login sends no email code. The admin and management `Add/UpdateGenericOIDCProviderRequest` take `email_verified` (field 9/10), and `zitadel.idp.v1.GenericOIDCConfig` and `zitadel.idp.v2.GenericOIDCConfig` return it (field 6, leaving 5 for v2's missing `use_pkce`). It's stored as `isEmailVerified` on the `*.idp.oidc.added`/`changed` events and in the new `projections.idp_templates6_oidc.is_email_verified` column (setup step `spalk_01_idp_templates6_oidc_add_is_email_verified`, `cmd/setup/spalk_01.{go,sql}`, named apart from upstream's numbered steps). Unlike Azure AD's, the provider (`oidc.WithEmailVerified`, `internal/idp/providers/oidc`) sets `email_verified` on the fetched user info itself rather than answering from the provider: `RetrieveIdentityProviderIntent` rebuilds a generic OIDC user from the intent's stored JSON with `oidc.InitUser()`, without the provider, so only a flag in the user's own data reaches the intent response (`idpInformation`, and the login's `CreateUser` request) and auto-linking. Console: a checkbox on the generic OIDC provider page (`IDP.EMAILVERIFIED`, new `IDP.EMAILVERIFIED_DESC` in `en.json` only). Tests: `internal/idp/providers/oidc/session_test.go` (incl. the JSON round trip), `internal/command/{idp_model,instance_idp,org_idp}_test.go`, `internal/query/{,projection/}idp_template_test.go`, `internal/api/grpc/{admin,management}/idp_converter_test.go`. On a rebase, check upstream hasn't taken these proto field numbers.
  - **Not yet for generic OAuth and SAML** (plan only): both mappers (`internal/idp/providers/oauth/mapper.go`, `saml/mapper.go`) return no email at all and `IsEmailVerified() == false`; the email comes from Actions or the login UI's own mapping. The same option would need, per type: (1) an `email_verified` request/config field, event field + `Change...IsEmailVerified`, write-model field and `idp_templates6_oauth2`/`idp_templates6_saml` column (one more `spalk_NN` setup step), as above; (2) an email to verify: an email attribute name on the provider (OAuth: like `id_attribute`, a JSON path into the user endpoint's response; SAML: an assertion attribute name) so `GetEmail` returns it; (3) the flag on the mapped user's own serialised data, not the provider: OAuth's intent user is rebuilt with `unmarshalRawIdpUser(intent.IDPUser, p.User())` and SAML's with a bare `&saml.UserMapper{}`, so add an exported, JSON-tagged `EmailVerified` field to each `UserMapper` set at mapping time (OAuth `FetchUser`, SAML `FetchUser` from the assertion) and have `IsEmailVerified` return it. Without (2) the flag does nothing, since a verified empty email isn't an email; until then such an IdP's sign-up keeps its email code.
- **An IdP that sends no email asks for one**, from `v4.19.4-spalk.10` (`apps/login/src/lib/server/idp-intent.ts`, `handleAutoCreation`; `src/lib/server/register.ts`, `registerUserAndLinkToIDP`; `src/components/register-form-idp-incomplete.tsx`): an IdP that leaves the email out (an Entra account without `mail`) made auto-creation call `CreateUser` with an empty email, which Zitadel refuses (`Errors.User.Email.Empty`), and the person saw "Login failed". Auto-creation now sends them to the complete-registration form, as for a missing name, where the email is editable when the IdP sent none (and read-only when it sent one). `registerUserAndLinkToIDP` uses the form's email only when the intent has none, creates it unverified with the IdP link, and the login has it verified with one code (below). Tests: `idp-intent.test.ts` (`CASE 4`), `register.test.ts`, `register-form-idp-incomplete.test.tsx`.
- **The complete-registration form sends one email code and verifies it**, from `v4.19.4-spalk.10` (`apps/login/src/lib/server/register.ts`, `registerUserAndLinkToIDP`): it kept the intent's `sendCode` and, with upstream's `checkEmailVerification` commented out, completed the login with the email unverified. It now creates the email unverified (`withoutCreateEmailCode`, as auto-creation does) and runs `checkEmailVerification` after the session is created, which sends the only code and goes to `/verify` (with `EMAIL_VERIFICATION=true`, which Spalk sets). A verified email is unchanged. Test: `register.test.ts`.
- **An auto-link the user-creation hook refuses shows the hook's message**, from `v4.19.4-spalk.10` (`apps/login/src/lib/server/idp-intent.ts`, `handleAutoLinking`): a failed `AddIDPLink` sent Zitadel's error text to `/linking-failed` in the URL, with its `[code]` prefix and ` (EXEC-…)` suffix. An Actions v2 target's refusal (`targetRefusalMessage`) is now returned to the IdP process page as its message, as auto-creation's is; other failures still go to `/linking-failed`. Test: `idp-intent.test.ts` (`CASE 3: Auto-linking by email`).
- **No code is sent to an email at a `.invalid` domain**, from `v4.19.4-spalk.10` (`apps/login/src/lib/client-utils.ts`, `isUndeliverableEmail`; `src/lib/server/loginname.ts`, `sendLoginname`; `src/lib/server/password.ts`, `resetPassword`): Spalk removes a member their organisation's directory manages by giving them the verified placeholder email `<userId>@removed.invalid` and removing their IdP links, so an SSO-only user is left with no authentication method. Login v2 sends a user with no password, passkey or IdP to `/verify?invite=true` and, their email being verified, emails an invite code, which a `.invalid` address (RFC 2606) can never receive: a dead end. An address whose domain is `invalid` or ends in `.invalid` (case-insensitive) now gets nothing: the login-name step answers "This account has no way to log in. Contact your organisation's administrator." (`loginname.errors.noLoginMethod`), and the password page's "Reset password" answers "This account's email address can't receive mail. Contact your organisation's administrator." (`password.errors.emailUndeliverable`), in `en.json` only (other locales fall back to it). Tests: `loginname.test.ts` (`Single user found - authentication method handling`), `password.test.ts` (`resetPassword`), `client-utils.test.ts`.
